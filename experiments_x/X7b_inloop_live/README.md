## Escalation rule (prop:attempts) per segment: predicted vs realized

Cells = (model, branch, k, source or pooled, basis, λ). `G` = p_k W_λ + (1−p_k)Δ_{k+1} − λ a_k with p_k, a_k, b, v_b estimated on the state set (v_h = 1); `realized` = paired mean of the per-task gain of attempting k (then continuing as the rule prescribes) over the direct Opus terminal. Sign agreement on CI-decided cells (realized CI excludes 0), next to the marginal-rate predictor (p_k replaced by the called model's unconditional attempt-1 rate) and the naive always-attempt / always-stop rates.

## Deviations and limitations

- n = 283 tasks (< 300): the EXEC-CLEAN runnable id_test frame after the uniform all-zero exclusion is the whole sample (Addendum applies the all-zero rule to bcb; here it is applied to every source because Opus's terminal outcome and W_lambda are degenerate on such tasks; 48 mbpp dim1 + 3 mbpp dim4 tasks affected).
- deepseek-v4-pro (thinking disabled) and deepseek-flash (reasoning on, max_tokens 2048, added on the coordinator's Addendum-2 request) are NON-BENCHMARK models: no recorded attempt 0, dollar costs use PROXY prices (Qwen3-Max and qwen3.5-plus list prices respectively); their primary bases are tokens and seconds. Their switch target is qwen3-max (not in the paper's chain). deepseek-flash completion tokens include its reasoning tokens.
- Feedback = hidden-test error message (tail of the sandbox stderr, <= 800 chars); for assert-style suites this reveals the failing assertion, so the retry gain mixes reusable work and test-information leakage (C4 reports the split by failure kind).
- The visible-verifier chains (C5) are replayed on the attempts generated under hidden-test feedback (a visible-verifier false reject would have produced a different feedback text, and a falsely rejected passing attempt has no live continuation and is sent to the Opus terminal), so the visible chain's quality loss and cost increase are upper bounds; the extraction follows ACRouter's run_visible_tests except that '>>>'/'...' continuation lines are dropped from the expected side and the <= 5 examples run in one sandbox process. In this frame 77/112 bcb prompts yield at least one clean call/expected pair; the other 35 carry only multi-statement doctests (setup lines), which ACRouter's regex would pair with the next '>>>' line and always fail (systematic false rejects); here they score the neutral 0.5 like prompts without examples (mbpp dim1 has none by construction).
- deepseek-flash truncation: with max_tokens 6144 its reasoning exhausted the completion budget on 101 attempts over both passes (finish_reason=length, empty content). HEADLINE = view (a): these stay in the sample as paid failures at the 6,144 budget (budget-matched with the other 249 flash roots). Per the coordinator's protocol the truncated attempts were also re-issued with the same messages at 16384 tokens under tag X7b:flash_rerun (originals in attempts_flash_truncated.jsonl); this is view (b), reported in its own section with its own attempt costs and never mixed into view (a); 24 re-runs still truncated and are censored there. Inside view (b) the retry/switch attempts of a replayed chain were regenerated from the re-run's real verdict and error message (the original downstream rows had been conditioned on an empty assistant turn and the feedback 'empty response').
- All live outputs are code-only (system prompt) with max_tokens 1024, temperature 0.7; recorded attempt-0 responses were free-form, so p_0 and p_1 differ in format as well as sampling.
- mbpp dim1 live prompts append 'Name the function `<entry_point>`' (the released prompt did not show the name and the MBPP+ harness calls it; without the name the failure set is dominated by naming mismatches that the NameError feedback fixes trivially). Attempt 0 for mbpp dim1 is therefore not prompt-matched to attempt 1.
- kimi-k2.5 has no live switch target (the next-stronger model is the recorded Opus terminal), so its switch branch is the terminal fallback; its 'switch' success is the recorded Opus pass rate on its failure set.
- Switch chains: qwen3.5-plus -> qwen3-max -> kimi-k2.5 (paper's chain, in full) and qwen3-max -> kimi-k2.5; the two non-benchmark roots switch to qwen3-max only (no third live attempt), to keep the kimi-k2.5 load (2 concurrent calls shared by all experiments) inside the 2-hour wall-clock.
- Small per-source failure sets (humaneval, he, hex) make most per-source cells CI-undecided; pooled cells carry the evidence. The split-half OOS test halves them again.
- Sandbox verification time is included in a_k (seconds basis); the visible-verifier time is not (it would replace it in the visible chain).
- Wall-clock: main live pass 123 min (1,415 chains; bounded by the kimi-k2.5 cap of 2 concurrent calls shared by all experiments, ~30 s per kimi call under load), deepseek-flash re-run pass 17 min; first-to-last attempt timestamp span 143 min. The main pass alone exceeds the 2-hour guidance for a from-scratch run; a re-run of run.py reads every call from the packy cache and finishes in seconds with zero live spend (this README was written by such a run: runtime 2.4 s).
- The recorded Opus latency/cost come from the benchmark's run (another day, another relay); live latencies are relay latencies under our concurrency.
- Files: `attempts.jsonl` (append-only raw log of every live attempt with tokens, latency, cost, verdicts and feedback-bearing texts; complete runs are delimited by `job_complete`), `attempts_view_a_6144.jsonl` (HEADLINE analysed rows = first complete run per chain, explicit `budget` field), `attempts_view_b_rerun16k.jsonl` (the replayed chains' last run), `attempts_flash_truncated.jsonl` (the original 6,144-token deepseek-flash attempts that returned no content), `recorded.jsonl` (attempt-0 verification), `partial_progress.json`, `results.json`, `figures/`, `run_main_pass.log` / `run_rerun_pass.log` (console logs of the two live passes), `probe.py` (the 8-call pre-flight probe of the four models, tag X7b, included in the spend). `integrator_check.py` was placed here by the integrator; note that it scans every row of `attempts.jsonl` (both passes), whereas the analysed set is view (a).
